# pr-comment

Write PR comments a human reviewer can take in at a glance, then post them only once the user approves.

## Style

- **Summary first.** Open with one or two plain sentences that give the answer or outcome. Don't label it `TL;DR:`; it is just the first line.
- **Few words.** Short sentences, short numbered or bulleted points. One point per view, caller, file or fix.
- **Concrete references.** Name routes, `file:line`, functions, commit SHAs, test names. A reviewer should be able to follow each claim to the code.
- **Facts only.** No opinions or decisions phrased as preferences: drop "so I'd keep them", "I'd rather not", "Leaving it as is", "I think".
- **No restating.** Cut any sentence that repeats what the summary or the points already show.
- **No filler.** No greetings, thanks, "Great question", or closing offers.
- **Footer.** End with `_Generated by [Claude Code](https://claude.ai/code)_` after a `---` line.

## Before writing

Verify every claim first: grep the code, including other repos it touches (for example the frontend that calls a DB endpoint), run the test, or measure. Don't write what you haven't checked. If checking turns up something that contradicts an earlier statement, the comment says what's true now.

## Workflow

1. **Find the target.**
   ```bash
   # top-level comments
   gh api --paginate repos/<owner>/<repo>/issues/<n>/comments \
     --jq '.[] | "\(.id) \(.user.login) \(.body[0:80])"'
   # inline comments; the first column is the thread's root id, the one to reply to
   gh api --paginate repos/<owner>/<repo>/pulls/<n>/comments \
     --jq '.[] | "\(.in_reply_to_id // .id) \(.id) \(.user.login) \(.path):\(.line) \(.body[0:80])"'
   ```
   Replies go to the thread's root comment. GitHub doesn't accept a reply to a reply.
2. **Draft** the comment and show it to the user. Revise until they approve. Don't post without approval.
3. **Post** from a file in the scratchpad, so quoting can't break the body:
   ```bash
   # reply in an inline review thread
   gh api -X POST repos/<owner>/<repo>/pulls/<n>/comments/<comment_id>/replies -F body=@reply.md --jq .html_url
   # top-level PR comment
   gh pr comment <n> -R <owner>/<repo> --body-file reply.md
   ```
4. **Edit** a posted comment instead of posting a correction:
   ```bash
   gh api -X PATCH repos/<owner>/<repo>/pulls/comments/<comment_id> -F body=@reply.md   # inline
   gh api -X PATCH repos/<owner>/<repo>/issues/comments/<comment_id> -F body=@reply.md  # top-level
   ```
5. Report the comment URL to the user.

## Replying to review findings

For each finding, say what changed and where, or why nothing changed:

> Fixed in abb691c: the `down` now recreates `organisations_offspring` as `STABLE`, the state `20260923150000` leaves.

If a suggestion would change behaviour rather than just implementation, list the affected callers and leave the decision to the reviewer or owner.

## Example

Too long, with opinion and restating:

> **TL;DR:** The portal needs organisations with no vessels, so I'd keep them. The `cache.policies` shortcut would change what the endpoint returns, not just its speed. Leaving it as is.
>
> The portal needs organisations with no vessels, so I'd rather not narrow the UWR branch …

House style:

> The portal needs organisations with no vessels.
>
> Views that call `rpc/organisations_vessels`:
>
> 1. **Organisations → Tree View** (`/organisations/treeview`, UWR). This is the call with no `id` filter, which returns every organisation. Each row becomes a tree node. If a parent with no vessels is missing, its whole subtree disappears.
> 2. **Organisation → Child organisations tab** (`/organisations/:id`). Same tree; the "Child organisations (N)" count counts organisation nodes.
> 3. **Cyber application/policy vessel lists** (via `useVessels`). These only use the vessels, so dropping empty organisations makes no difference here.
>
> A vessels-only shortcut fits only 3 and needs its own endpoint.
